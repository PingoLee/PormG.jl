## Schema management reads generated columns, and needs PostgreSQL 13 (#1032)

- **Version**: Unreleased
- **PormG ref**: #1032, #1108 ; `src/migrations/introspection.jl` (`get_database_schema`, `_pg_live_table`), `src/column_ir.jl` (`GeneratedExpression`, `_defaults_equal`)
- **Recorded**: 2026-10-09
- **Severity**: breaking (narrow): schema management on PostgreSQL 11 and 12 stops working; behavior change everywhere else. `makemigrations`, `migrate`, `check` and `inspectdb` raise `BackendCapabilityError` on a PostgreSQL server older than 13. A generated column is read as generated, not as an expression default. Queries and writes are unchanged.

### What changed

`SearchVectorField(generated_from = …, config = …, weights = …)` declares a generated column
(`GENERATED ALWAYS AS (…) STORED`) that PostgreSQL keeps current. To diff one, the schema reader now
asks `pg_attribute.attgenerated`, which PostgreSQL 12 added, and removing `generated_from` plans
`ALTER COLUMN … DROP EXPRESSION`, which PostgreSQL 13 added. Schema management therefore needs 13
(#1108), so that every plan it produces runs on every server it accepts. For an app that does not use
the new keywords, that changes the following:

| | before | after |
|---|---|---|
| `makemigrations` / `migrate` / `check` / `inspectdb` on PostgreSQL 11 or 12 | ran | `BackendCapabilityError` naming the 13+ requirement, before the schema query runs |
| a generated column made by hand, under a plain declaration | read as an expression default; nothing planned | read as generated; still nothing planned (PormG did not create it) |
| `inspectdb` on a generated column | wrote `db_default = (postgres = "<expression>",)` | writes the plain field and warns, or `generated_from`/`config`/`weights` for a `tsvector` column PormG created |
| `check` on a generated column | reported it as an expression default to declare with `db_default=` | not reported |
| a pending plan written before upgrading, for a table that has a generated column | applied | refused by the schema precondition (the table's fingerprint now records the column as generated) |

Queries and writes read no catalog, so they have no new floor.

### Who this affects

- Apps whose `makemigrations`/`migrate` runs against PostgreSQL 11 or 12.
- Models files generated by `inspectdb` from a table that has a generated column: the column carries
  a `db_default = (postgres = …)` holding the generation expression.
- A plan generated before upgrading and not yet applied, for a table with a generated column.

### How to find the calls to migrate

```bash
psql -Atc "SHOW server_version"                    # schema management needs 13 or newer
psql -Atc "SELECT attrelid::regclass, attname FROM pg_attribute WHERE attgenerated <> ''"
```

The second query lists the generated columns. In a generated models file, look for those columns'
`db_default = (postgres = …)`. `migrate` names a refused plan's table in its precondition error.

### Migrate your app

```julia
# ✗ before — inspectdb wrote the generation expression as a database default
search = Models.SearchVectorField(db_default = (postgres = "to_tsvector('simple'::regconfig, title)",))
# ✓ after — the keyword describes no default the column has; nothing is planned against a generated
# column PormG did not create, with or without it. Delete it, or declare the column generated, which
# re-creates it as PormG's own on the next migration (a destructive plan)
search = Models.SearchVectorField()
search = Models.SearchVectorField(generated_from = ("title",), config = "simple")
```

For a refused pending plan, run `makemigrations()` again. On PostgreSQL 11 or 12, upgrade the
server before running schema management.
