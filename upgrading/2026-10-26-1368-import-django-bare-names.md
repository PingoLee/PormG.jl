## The Django importer writes column names bare in CHECK and index SQL (#1368)

- **Version**: 0.9.0
- **PormG ref**: #1368 ; `src/migrations/importers.jl` (`_q_ident`), `src/migrations/introspection.jl` (`_comparable_sql_text`)
- **Recorded**: 2026-10-26
- **Severity**: behavior change, PostgreSQL and SQLite. `import_models_from_django` writes a different SQL text for a converted `CheckConstraint`, a partial index or constraint condition, and a functional index. After a re-import, `makemigrations` on PostgreSQL drops and re-creates, once, each such object whose stored text is not the new text exactly — most of them — and that plan is destructive. On SQLite nothing is re-created. MySQL is unreleased.

### What changed

The importer turns a Django `CheckConstraint(check=Q(…))`, an index `condition=Q(…)` and a functional
index (`Lower("surname")`) into SQL over the table's columns. It wrote every column double-quoted, as
Django renders it. On MySQL a double-quoted name is a string literal, so that text made a CHECK
over a constant and an index on one. `makemigrations` on MySQL now refuses it.

The importer now writes a column bare when it is a plain lower-case name that no engine reserves.
That spelling is the column on PostgreSQL, SQLite and MySQL alike. A name some engine reserves
(`user`, `order`) or one not in lower case keeps Django's double quotes: no other spelling is the
column on every engine.

| `check=Q(laps__gte=0) & Q(grid__lte=F("laps"))` | before | now |
|---|---|---|
| imported condition | `"laps" >= 0 AND "grid" <= "laps"` | `laps >= 0 AND grid <= laps` |
| `Index(Lower("surname"), name=…)` | `LOWER("surname")` | `LOWER(surname)` |

To keep a database Django built adopting the import with nothing planned, `makemigrations` now
compares the declared and the live text of a CHECK, a partial index or a functional index with a
double-quoted portable name read as the bare one. SQLite keeps Django's text as Django sent it,
quotes included. A CHECK PormG did not create whose text differs from the declaration only by those
quotes is adopted, where it was replaced (on SQLite, a table rebuild). The ownership markers are
unchanged: they still hash the declared text as written.

A database that **PormG** created from the old import's text carries the old text's marker. After a
re-import the declared text changes, so the marker no longer matches, and the object is kept only
when the database's own text compares equal to the new declaration:

| object created from the old text, declared with the new | SQLite | PostgreSQL |
|---|---|---|
| `CheckConstraint`, partial-index condition | nothing planned | kept only when PostgreSQL stores the new text exactly, as for a single comparison over a non-text column (`laps >= 0`); otherwise dropped and re-created once |
| functional index (`expressions`) | nothing planned | dropped and re-created once |

SQLite stores the text as PormG sent it, which compares equal to the new one. PostgreSQL stores its own
deparse: `((laps >= 0) AND (grid <= laps))` for `laps >= 0 AND grid <= laps`, a cast on a text column
(`((code)::text = 'x'::text)`), `= ANY (ARRAY[…])` for an `IN`, and `lower((surname)::text)` for
`LOWER(surname)`, none of which is the new declaration. The drops make the plan destructive, so a
non-interactive `migrate` of it needs `destructive = true`.

### How to find the calls to migrate

Look for a models file generated by `import_models_from_django` that declares a `Models.CheckConstraint`, an `Index` or `UniqueConstraint` with `condition =` or
`expressions =` whose SQL double-quotes a column. Nothing changes for a models file you keep. Only a
**re-import** writes the new text.

### Migrate your app

Either keep the generated models file as it is, which is still correct on PostgreSQL and SQLite, or
re-import and apply the one-time plan, which on PostgreSQL re-creates most imported CHECKs and indexes
(`migrate(…; destructive = true)` when it runs non-interactively):

```julia
# ✓ either: keep the old declaration on PostgreSQL / SQLite
Models.CheckConstraint(condition = "\"laps\" >= 0", name = "result_laps_ck")

# ✓ or: the new import's text, which MySQL takes too
Models.CheckConstraint(condition = "laps >= 0", name = "result_laps_ck")
```

On MySQL only the bare spelling is accepted: `makemigrations` refuses a double-quoted name there
with `InvalidMigrationError`, naming the bare spelling.
