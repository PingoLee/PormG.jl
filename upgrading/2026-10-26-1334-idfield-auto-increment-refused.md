## `IDField(auto_increment = …)` raises `FieldValidationError`; `generated` controls identity (#1334)

- **Version**: Unreleased
- **PormG ref**: #1334 ; `src/models/fields.jl` (`IDField`, `_reject_retired_idfield_kwargs`), `src/migrations/column_spec.jl` (`_inspectdb_id_pk`)
- **Recorded**: 2026-10-26
- **Severity**: breaking. A model that declared `IDField(auto_increment = …)` raises when it is defined.

### What changed

`IDField` accepted `auto_increment`, stored it, and no DDL path read it. On PostgreSQL the identity
follows `generated`, and SQLite and MySQL auto-increment every `IDField` key. So
`IDField(auto_increment = false)` read as "a key the database does not generate" and still rendered an
identity column:

```sql
"raceid" bigint PRIMARY KEY UNIQUE NOT NULL GENERATED BY DEFAULT AS IDENTITY
```

An explicit id still inserted, so nothing failed. But a later `create()` without an id drew from the
identity sequence, which could collide with the explicit ids, and the schema said something
different from the model.

The keyword now raises `FieldValidationError`, whatever its value, and points at `generated = false`.
One keyword controls identity:

| Declaration | PostgreSQL | SQLite | MySQL |
|---|---|---|---|
| `IDField()` | `bigint … GENERATED BY DEFAULT AS IDENTITY` | `INTEGER PRIMARY KEY AUTOINCREMENT` | `BIGINT … AUTO_INCREMENT PRIMARY KEY` |
| `IDField(generated = false)` | `bigint PRIMARY KEY UNIQUE NOT NULL`, no identity | unchanged | unchanged |
| `IDField(auto_increment = false)` | was the identity column above | was `IDField()` | was `IDField()` |
| | now `FieldValidationError` | now `FieldValidationError` | now `FieldValidationError` |

`generate_models_from_db` on SQLite wrote `auto_increment=false` for a primary key that is not an
exact `INTEGER` (a `BIGINT PRIMARY KEY`, for example), and for a key of a type PormG has no field
for. It no longer does. A models file it wrote before this change raises on load.

At write time, `create`, `save`, `bulk_insert` and `allocate_primary_keys` treat every `IDField` key
as one the database can generate, as they always did for an `IDField` without
`auto_increment = false`. That changes one population: a SQLite model `generate_models_from_db` wrote
with `auto_increment=false` (a key that is not an exact `INTEGER`), once regenerated. Its key now
goes through every generated-key path:

| On such a table | before | now |
|---|---|---|
| `allocate_primary_keys(df)` | the frame unchanged | ids filled from the table's highest id |
| `bulk_insert(df; returning = …)` with no key column | `QueryBuildError` | ids pre-allocated, rows written |
| `create()` with no id, after `allocate_primary_keys` in the same transaction | `IntegrityError` (NOT NULL) | the next reserved id |
| `bulk_insert` with an all-blank key column | `InvalidValueError`, nothing sent | the column is left out; SQLite raises `IntegrityError` (NOT NULL) |
| `bulk_insert`/`bulk_copy` with some blank key cells | `InvalidValueError` | `QueryBuildError` (mixed blank and explicit values) |

`create()` with no id outside such a transaction fails with NOT NULL either way, and an explicit id
inserts either way.

### How to find the calls to migrate

```
grep -rn 'auto_increment' models/ db/
```

Include generated model files. The load error names the keyword.

### Migrate your app

```julia
# ✗ before: stored, never rendered — PostgreSQL still had an identity column
raceid = Models.IDField(auto_increment = false)
# ✓ after: a key the caller supplies; PostgreSQL renders no identity
raceid = Models.IDField(generated = false)

# ✗ before: the default, spelled out
raceid = Models.IDField(auto_increment = true)
# ✓ after
raceid = Models.IDField()
```

Switching to `generated = false` changes the PostgreSQL column: the next `makemigrations` plans
dropping the identity. Every explicit id stays. Inserting without an id then fails with a NOT NULL
violation, where it used to draw from the sequence. `allocate_primary_keys` cannot reserve ids for
such a key on PostgreSQL either: there is no sequence to draw from, and it returns the frame with the
ids missing, so supply every id yourself. A generated models file can be regenerated with
`generate_models_from_db`, or the keyword deleted by hand; on SQLite the column is unchanged either
way.
