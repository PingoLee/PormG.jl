## `IDField(auto_increment = …)` raises `FieldValidationError`; `generated` controls identity (#1334)

- **Version**: Unreleased
- **PormG ref**: #1334 ; `src/models/fields.jl` (`IDField`, `_reject_retired_idfield_kwargs`), `src/migrations/column_spec.jl` (`_inspectdb_id_pk`)
- **Recorded**: 2026-10-26
- **Severity**: breaking. A model that declared `IDField(auto_increment = …)` raises when it is defined.

### What changed

`IDField` accepted `auto_increment`, stored it, and no DDL path read it. On PostgreSQL the identity
follows `generated`, and SQLite and MySQL auto-increment every `IDField` key. So
`IDField(auto_increment = false)` read as "a key the database does not generate" and still rendered an
identity column:

```sql
"raceid" bigint PRIMARY KEY UNIQUE NOT NULL GENERATED BY DEFAULT AS IDENTITY
```

An explicit id still inserted, so nothing failed. But a later `create()` without an id drew from the
identity sequence, which could collide with the explicit ids, and the schema said something
different from the model.

The keyword now raises `FieldValidationError`, whatever its value, and points at `generated = false`.
One keyword controls identity:

| Declaration | PostgreSQL | SQLite | MySQL |
|---|---|---|---|
| `IDField()` | `bigint … GENERATED BY DEFAULT AS IDENTITY` | `INTEGER PRIMARY KEY AUTOINCREMENT` | `BIGINT … AUTO_INCREMENT PRIMARY KEY` |
| `IDField(generated = false)` | `bigint PRIMARY KEY UNIQUE NOT NULL`, no identity | changed by #1393 | changed by #1393 |
| `IDField(auto_increment = false)` | was the identity column above | was `IDField()` | was `IDField()` |
| | now `FieldValidationError` | now `FieldValidationError` | now `FieldValidationError` |

`generate_models_from_db` on SQLite wrote `auto_increment=false` for a primary key that is not an
exact `INTEGER` (a `BIGINT PRIMARY KEY`, for example), and for a key of a type PormG has no field
for. It no longer does: since #1393 it writes `IDField(generated = false)` for such a key, a key the
caller supplies on every engine. A models file it wrote before this change raises on load.

What `generated = false` does on SQLite and MySQL, and at write time on every engine
(`allocate_primary_keys`, `bulk_insert`, `create`), is the #1393 entry's: the two changes ship in one
train, and that entry states the result.

### How to find the calls to migrate

```
grep -rn 'auto_increment' models/ db/
```

Include generated model files. The load error names the keyword.

### Migrate your app

`auto_increment = false` has two valid replacements. They declare the same key; they differ in
whether the next `makemigrations` changes the table:

```julia
# ✗ before: stored, never rendered — the table PormG created has an identity column
raceid = Models.IDField(auto_increment = false)

# ✓ after, keeping the table as it is: the identity stays, unused while every insert supplies an id
raceid = Models.IDField()

# ✓ after, declaring a key the caller supplies: the next makemigrations drops the identity
raceid = Models.IDField(generated = false)

# ✗ before: the default, spelled out
raceid = Models.IDField(auto_increment = true)
# ✓ after
raceid = Models.IDField()
```

Because the keyword never reached the DDL, a table PormG created from such a model is the
`IDField()` table: an identity column on PostgreSQL, an auto-increment key on SQLite and MySQL.
`IDField()` describes that table exactly, so `makemigrations` plans nothing, and every insert that
supplies its id keeps working as before. Choose it when the code supplies every id and you do not
want a schema change in this upgrade, for example a staging table that is emptied and refilled with
explicit ids.

`generated = false` describes what the code means, and it changes the column: the next
`makemigrations` plans dropping the identity on PostgreSQL (and, since #1393, a rebuild on SQLite and
a `MODIFY COLUMN` on MySQL). Every explicit id stays. Inserting without an id then fails, where it
used to draw from the sequence, and `allocate_primary_keys` raises `QueryBuildError` for such a key
(#1393), so supply every id yourself. Choose it when you want the schema to say the key is the
caller's, and review the planned migration before you apply it.

A models file that `generate_models_from_db` wrote is the other case: it read a table whose key the
database does not fill, so `generated = false` is the declaration that matches that table, and it is
what the generator writes now. Regenerate the file, or replace the keyword by hand.
