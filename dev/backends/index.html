Backend Capabilities

PormG runs on PostgreSQL, SQLite and MySQL (see the MySQL Guide). Most of what PormG does means the same on every backend. Some features exist on one backend only, and PormG does not emulate a feature a backend lacks. It raises BackendCapabilityError instead, and the message names the feature, the backend you are on, and the backends that support it:

The @jcontains lookup (JSONB @>) needs JSONB containment and key operators (`@>`, `?`, `?|`, `?&`),
which SQLite does not support (supported on PostgreSQL).

The table below is the list PormG checks. A unit test fails when this page and the code disagree.

Some features exist from a server version on. Their cell says which, as from 13 (PostgreSQL's server_version_num major version) or from 3.25.0 (the SQLite library PormG loads). PormG asks the server its version where it needs the answer; an offline SQLite key is checked against the server_version it states, and a refusal names that key instead of a library (Testing). Where a feature is refused, an older server gets BackendCapabilityError naming both versions:

A window function needs SQLite 3.25.0 or newer, for window functions (`OVER (…)`); the SQLite
library PormG loads is 3.24.0.

Where PormG reads the schema, an older server is not refused: the feature reads as absent, which is exact there, because a server without the feature has none of it.

Guarantees that rest on an engine feature

Some promises PormG makes hold because the engine underneath provides something, not because PormG computes them. Each backend keeps them in its own way, and its column says how. Where a backend cannot keep a promise, PormG refuses or documents the difference rather than emulating it.

Three promises are PormG's own meaning rather than an engine's, and hold on every backend by construction: F("grid") / 2 divides integers as integers, a NULL Concat operand is skipped, and Cast(x, "smallint" | "integer" | "bigint") raises StatementError with sqlstate == "22003" on a value outside the type, on the row, in every clause. PostgreSQL's cast does that itself; MySQL's SIGNED is 64-bit and SQLite's INTEGER applies no range below 64 bits, so there PormG renders a guard that raises it (#1356). A declared output_field of the same type on Coalesce, Greatest, Least or Case is the same cast over the whole function, and renders the same guard (#1405). One limit: SQLite saturates a value past 64 bits to the largest integer, which nothing can tell from a real one, so a bigint cast there is not guarded. The guard names its operand three times, so every value it binds is bound three times, and a Subquery operand runs three times per row. The cost compounds when declarations nest: a declared Coalesce over a declared Case binds the Case's values nine times. A backend whose operator computes something else gets a different rendering, not a different answer (Functions and Dates).

MySQL

MySQL 8.4 or newer is supported through MySQL.jl 2.0. The tables above have its column. What it means for a query, a write and a migration, from its collation to its non-transactional DDL, is on the MySQL Guide.

What the capability table leaves out

  • A version PormG does not check. ON CONFLICT (bulk_insert(on_conflict = …), update_or_create, get_or_create) needs SQLite 3.24, and an older library raises SQLite's own error. A query feature newer than your PostgreSQL server fails with PostgreSQL's own error (PostgreSQL Guide).
  • A number that depends on a version or a driver. SQLite accepts 999 bind parameters per statement before 3.32 and 32766 from it. PormG sizes bulk_insert and bulk_update batches to the library it loads, so this is a limit, not a feature. On MySQL the limit is MySQL.jl's, 4096 parameters per statement (the protocol itself allows 65535): the bulk writers split under it, and any other statement past it (a __@in list of 5000 values) is refused with QueryBuildError before it is sent. On PostgreSQL the limit is the driver's: LibPQ binds the protocol's 65535 parameters per statement, and Postgres.jl binds 32767 (JuliaDatabases/Postgres.jl#34). A many-to-many remove of more ids than that is split by PormG under the limit of the driver the pool uses, and so is a MySQL or SQLite add; PostgreSQL's add binds its targets as one array.
  • A feature one backend supports only in part. For example, ToChar formats or Extract parts that SQLite cannot spell, or a cast to a time type. Each raises BackendCapabilityError where it is used, and its page says which forms work.
  • A gap in PormG, not in an engine. SQLite has explicit window frames, but PormG does not render WindowOver(frame = …) there yet, and raises BackendCapabilityError saying so (Window Functions).
  • A difference in what a query returns. When backends would compute different values or rows for the same query, PormG refuses it on the backend that departs, or documents the difference. That is not a missing feature (Functions and Dates; for a declared scale or a cast to an integer, Rounding).
