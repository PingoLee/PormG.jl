Quick Start & Setup

The easiest way to get PormG running in a new project is through the interactive setup tool.

Interactive Setup

To create a new database configuration folder and connection file (defaults to db if no argument is provided):

using PormG

# Default (creates "db" folder)
PormG.setup()

# Custom folder
PormG.setup("db_bs")

What Setup Does

  • Creates the configuration folder (e.g., db/ or db_bs/).
  • Generates a template connection.yml with dev, test, and prod sections.
  • Creates a customizable models file (e.g., models.jl or my_models.jl) with the correct module boilerplate.
  • Optionally installs AI-assisted developer skills (pormg-usage) into the project, under .github/skills/ and .claude/skills/. The prompt names the folder it will write to.

Setting up another project's folder

Without root, both the folder and the skills are relative to the working directory, so PormG.setup("db") is meant to be run from the project root. An absolute path without root puts the configuration there and still offers the skills to the working directory; the prompt names that folder. A script that scaffolds a project somewhere else passes that project's root instead of changing directory. root has the same meaning it has for load:

const APP_ROOT = "/srv/race_control"

PormG.setup("db"; root = APP_ROOT)
# APP_ROOT/db/connection.yml, APP_ROOT/db/models.jl
# APP_ROOT/.github/skills/pormg-usage/ and APP_ROOT/.claude/skills/pormg-usage/SKILL.md

The folder is joinpath(root, "db") and the skills go into root, whatever the working directory is. As with load, the path must be relative when root is given.

Static Configuration (File-based)

If you already have a connection.yml, you can load it directly:

using PormG, LibPQ   # load SQLite or MySQL instead for those adapters

# Load the configuration folder (e.g., "db")
# This MUST happen BEFORE importing models!
PormG.Configuration.load("db"; env="dev")

# Now import your models
PormG.@import_models "db/models.jl" models
import .models as M

# Use the models
query = M.Driver.objects.filter("surname" => "Senna")
df = query |> DataFrame
`load()` must come before `@import_models`

The order in the snippet above is a requirement, not a style preference. @import_models calls set_models(...), which binds the models to a configuration that is already loaded. When none matches the models folder, it raises InvalidConfigurationError, naming the load call to add. PormG does not load the folder itself, because that load would choose the environment for you. A REPL keeps that convenience: there the folder is loaded, with a warning (#1248). See The Boot-Time Hazard for the full explanation.

The Bootstrap Sequence

The sequence is always the same three steps:

  1. Choose the environment (dev, prod, test) — and pass it, see below.
  2. Load the database configuration folder.
  3. Import your models.

A package or a service does steps 1–2 in a helper, called from the module body and from __init__, with an explicit root so the key does not depend on the working directory:

module RaceControl

using PormG, LibPQ

const DB_DIRS  = ["db"]
const APP_ROOT = normpath(joinpath(@__DIR__, ".."))

_load_configs() =
    PormG.Configuration.load_many(DB_DIRS; root = APP_ROOT, env = get(ENV, "RACECONTROL_ENV", "dev"))

_load_configs()                                   # module body: @import_models binds to it
PormG.@import_models "../db/models.jl" models
import .models as M

__init__() = _load_configs()                      # runtime: the image's configuration does not survive

end

This is the default to write. The snippet under Static Configuration above is the REPL / script form: one process, no precompilation, so one load is enough. Why the package needs both loads, and what each one fixes, is in The Boot-Time Hazard, under Loading before @import_models is not enough for a package. The rules this sequence relies on:

  • registering models never loads a folder outside a REPL — it refuses, naming the load call;
  • outside a REPL the environment comes from env= or PORMG_ENV, never from default_env:;
  • loading a folder again with the same environment is free;
  • a restored package image rebinds its models to the key they were imported under, or refuses.

Environment Selection

PormG supports explicit environment loading via env:

PormG.Configuration.load("db"; env="prod")

This is the preferred method for server applications, as it avoids relying on global ENV state. If env is not provided, PormG reads ENV["PORMG_ENV"] (a blank value counts as unset).

With neither, what happens depends on the session (#1228):

  • In a REPL (isinteractive()), PormG falls back to a top-level default_env: key in connection.yml, then to dev, and logs at @info which of the two decided.
  • Anywhere else — a service, a test, a script — load raises InvalidConfigurationError naming the call to fix. default_env: dev is production in many deployments, and a process nobody watches must not pick it.

A package passes env in its own load calls. Its __init__ runs in whatever session loads it, and using RaceControl at a REPL makes that session interactive: an env-less load there would take the REPL fallback (with the @info) rather than fail.

The REPL check is the same one that decides the implicit load of an unloaded models folder (#1248), so the bootstrap follows one rule: an interactive session gets the conveniences and is told when one of them decided, and every other process gets only what was stated.

Loading again

Calling load for a folder that is already loaded with the same environment does nothing: it returns the key, keeps the pool and any connection checked out of it, and does not read connection.yml again. So a bootstrap step that loads the configuration is safe to repeat. Two cases do reload, closing the pool and building a new one:

PormG.Configuration.load("db"; env = "staging")             # another environment: reload, with a warning
PormG.Configuration.load("db"; env = "dev", force = true)   # re-read an edited connection.yml

Loading from a project root

load("db") uses the string you pass for two things: the connection key your models bind to, and the folder it reads connection.yml from, resolved against the working directory. That works when you run from the project root. A server, a precompiled package or a test runner usually does not, so pass the root explicitly:

const APP_ROOT = normpath(joinpath(@__DIR__, ".."))

PormG.Configuration.load("db"; root = APP_ROOT, env = "prod")

With root, the key is still "db" (the string as passed), and the folder is joinpath(APP_ROOT, "db"), from any working directory. That folder is stored absolute as settings.db_def_folder. Everything that reads it resolves against the root instead of pwd(): makemigrations and migrate, the models file, and a relative SQLite database:. Leave root out and load behaves exactly as before. The path must be relative when root is given. An absolute one is refused, since joinpath would silently discard the root.
