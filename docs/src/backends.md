# Backend Capabilities

PormG runs on PostgreSQL and SQLite. MySQL is in progress for the first registered release ([#1130](https://github.com/PingoLee/PormG.jl/issues/1130)); see [MySQL (in progress)](@ref) for what works today. Most of what PormG does means the same on every backend. Some features exist on one backend only, and PormG does not emulate a feature a backend lacks. It raises `BackendCapabilityError` instead, and the message names the feature, the backend you are on, and the backends that support it:

```text
The @jcontains lookup (JSONB @>) needs JSONB containment and key operators (`@>`, `?`, `?|`, `?&`),
which SQLite does not support (supported on PostgreSQL).
```

The table below is the list PormG checks. A unit test fails when this page and the code disagree. MySQL's column says what it has today: a row it gains in a later phase of #1130 reads `no` until then, and is refused with `BackendCapabilityError` like any feature a backend lacks.

Some features exist from a server version on. Their cell says which, as `from 13` (PostgreSQL's `server_version_num` major version) or `from 3.25.0` (the SQLite library PormG loads). PormG asks the server its version where it needs the answer. Where a feature is refused, an older server gets `BackendCapabilityError` naming both versions:

```text
A window function needs SQLite 3.25.0 or newer, for window functions (`OVER (…)`); the SQLite
library PormG loads is 3.24.0.
```

Where PormG reads the schema, an older server is not refused: the feature reads as absent, which is exact there, because a server without the feature has none of it.

## Guarantees that rest on an engine feature

Some promises PormG makes hold because the engine underneath provides something, not because PormG
computes them. They hold on PostgreSQL and SQLite, each in its own way. A backend added later states
its own column here (MySQL's is in progress): where it cannot keep a promise, PormG refuses or
documents the difference rather than emulating it.

| Promise | PostgreSQL | SQLite | MySQL |
|---|---|---|---|
| Atomic migrations: `migrate` applies a plan whole, and a failed statement leaves nothing applied ([Migrations](migrations/workflow.md)) | transactional DDL | transactional DDL, inside `BEGIN IMMEDIATE` | **no**: each DDL statement commits on its own (`transactional_ddl`, [#1268](https://github.com/PingoLee/PormG.jl/issues/1268)). A plan of more than one statement runs only with `migrate(…; atomic = false)`; a failed statement leaves the ones before it applied and records the plan as `failed`, and `makemigrations` then plans what is missing |
| Two instances running `migrate` at once apply a plan once ([Deploying](migrations/deploying.md)) | an advisory lock | the database write lock (`BEGIN IMMEDIATE`) | a named lock (`GET_LOCK`), server-wide, so migrations of two databases on one server also wait for each other |
| Writes return their row: `create`, `get_or_create` and `update_or_create` return what they wrote, generated columns included ([Creating rows](write/create.md)) | `INSERT … RETURNING *` | no `RETURNING`: the `INSERT`, then a `SELECT` of the row on the same connection, in one transaction | no `RETURNING`: the `INSERT`, then a `SELECT` of the row on the same connection: `create` by its primary key (the `AUTO_INCREMENT` id the `INSERT` reports, or the key it supplied), `get_or_create` and `update_or_create` by their lookup |
| Upserts: `bulk_insert(on_conflict = …)`, `update_or_create`, and a race-safe `get_or_create` ([Bulk operations](write/bulk.md)) | `INSERT … ON CONFLICT` | `INSERT … ON CONFLICT` (SQLite 3.24 or later); `get_or_create` also runs under the write lock | `ON DUPLICATE KEY UPDATE`, which names no target ([#1267](https://github.com/PingoLee/PormG.jl/issues/1267)): `update_or_create` runs only when its lookup is the one unique key the row can conflict on (`upsert_conflict_target`), and reads `created` from the statement's report, or from a pre-check when the primary key is not `AUTO_INCREMENT`. `get_or_create` is a plain `INSERT` whose duplicate-key error re-reads the winner. Either lookup must be a unique key declared on the model. `bulk_insert(on_conflict = …)`: a targeted `DO NOTHING` or a `DO UPDATE` runs only when the target is the one unique key the rows can conflict on; an untargeted `:nothing` skips a conflict on any key, as everywhere. The `DO NOTHING` count comes from MySQL's report of each multi-row `INSERT` |
| Row locks: `select_for_update()` locks the rows it reads until the transaction ends ([Transactions](write/transaction.md)) | `FOR UPDATE` (and `of`, `nowait`, `skip_locked`, `no_key`); refused outside a transaction | no lock clause: inside `run_in_transaction` / `atomic` the transaction's `BEGIN IMMEDIATE` holds the database write lock until it ends; refused outside a transaction, as on PostgreSQL | `FOR UPDATE` (and `of`, `nowait`, `skip_locked`; `no_key` is refused); refused outside a transaction |
| A transaction may write a child before its parent; foreign keys are checked at `COMMIT` ([Transactions](write/transaction.md)) | the foreign keys PormG's migrations create are `DEFERRABLE INITIALLY DEFERRED` | `PRAGMA defer_foreign_keys` in the transactions PormG opens (`run_in_transaction`, `atomic`, `delete`) | **no**: InnoDB checks a foreign key at each statement ([#1272](https://github.com/PingoLee/PormG.jl/issues/1272)), so a child written before its parent raises `IntegrityError` at once. `delete()` runs children first, as on every engine, and refuses a delete whose rows' foreign keys form a cycle with `QueryBuildError`, as on every engine; `without_foreign_keys` raises `BackendCapabilityError` (`deferred_foreign_keys`) |
| Case-sensitive text: `@contains`, `@startswith`, `@endswith` and a plain equality respect case ([Filters](read/filters_and_aggregates.md)) | a deterministic collation (the default) | `BINARY` comparison, and `PRAGMA case_sensitive_like = ON`, which PormG sets | the `utf8mb4_0900_bin` collation of the columns PormG creates and of each connection ([#1265](https://github.com/PingoLee/PormG.jl/issues/1265)) |
| A query waits without blocking other tasks ([Async](async.md)) | non-blocking driver I/O, in parallel across connections | one worker task, shared by every SQLite database in the process, runs statements one at a time; the calling task yields while it waits | each statement runs on a task of its own, in parallel across connections; the calling task yields while it waits |

Two promises are PormG's own meaning rather than an engine's, and hold on every backend by
construction: `F("grid") / 2` divides integers as integers, and a NULL `Concat` operand is skipped.
A backend whose operator computes something else gets a different rendering, not a different answer
([Functions and Dates](read/functions_and_dates.md)).

## MySQL (in progress)

MySQL support is being built in phases ([#1130](https://github.com/PingoLee/PormG.jl/issues/1130)). The capability table and the guarantees table above have its column; a promise a later phase delivers says so there. What works today:

- `adapter: MySQL` in `connection.yml` ([connection.yml](configuration/connection_yml.md)), with `using MySQL` (MySQL.jl 2.0) loading the extension.
- **MySQL 8.4 or newer.** A connection to an older server is refused when it opens, with a `BackendCapabilityError` naming both versions. A MariaDB server is refused with an `InvalidConfigurationError`: it is planned as a separate backend.
- The connection pool, raw `fetch` with `?` placeholders, `run_in_transaction` / `atomic`, and `with_advisory_lock` (`GET_LOCK`).
- Server errors arrive as `IntegrityError`, `OperationalError` or `StatementError`, classified by MySQL's error number.
- **Single-row writes and deletes**: `create`, `update` (it returns the rows it matched, a row it left unchanged included), `save`, and `delete` with its cascades. MySQL refuses a subquery that reads the table an `UPDATE` or `DELETE` writes (error 1093), so a joined filter's selection and a membership subquery (`"id__@in" => queryset`, and each cascade step's subquery over its parents) are read through a derived table. A correlated one cannot be, and MySQL's error 1093 still reaches you for it, for a scalar `Subquery` over the table being written, and for a joined filter whose joins lead back into that table. An `update` whose `SET` reads a joined table renders MySQL's multi-table `UPDATE t AS a, … SET a.col = …`. MySQL assigns an `UPDATE`'s `SET` items in order, so an item that reads a column an earlier item writes (`update("laps" => F("grid"), "grid" => F("laps"))`) is refused with `QueryBuildError`, and in the multi-table form any item that reads another written column, since MySQL leaves that order unspecified. An item reading its own column (`F("laps") + 1`), or, in a single-table `UPDATE`, a column a later item writes, builds.
- **Upserts**: `update_or_create` and `get_or_create` ([Creating rows](write/create.md#Update-or-Create)). `update_or_create` is `INSERT … ON DUPLICATE KEY UPDATE`, which updates whichever row a unique key matched, so it runs only when the lookup is the one unique key the row can conflict on and raises `BackendCapabilityError` (`upsert_conflict_target`) otherwise. `get_or_create` is a plain `INSERT` whose duplicate-key error re-reads the winner. For both, the lookup must be a unique key declared on the model.
- **Bulk inserts**: `bulk_insert` with `on_conflict` and `returning` ([Bulk operations](write/bulk.md)). One `?` per cell, up to 65,535 parameters per statement. A targeted `on_conflict` or a `DO UPDATE` needs its target to be the one unique key the rows can conflict on (`upsert_conflict_target`), read from the frame: a column takes part when it is inserted and non-NULL in at least one row. The skipped rows of `on_conflict = :nothing` are counted from MySQL's report of each multi-row `INSERT` (`Records: N  Duplicates: D`, in whatever language the server writes it); a one-row chunk is sent without the clause, and its duplicate-key error is the skip. A `DO UPDATE` counts every row of the chunk. MySQL's `DO NOTHING` is an update that writes nothing, so it locks each existing row it meets until the transaction ends and can fire the table's `UPDATE` triggers, where PostgreSQL's skips without either. `returning` reads the rows back on the transaction's connection, by a key the DataFrame carries or the `on_conflict` target; for an `AUTO_INCREMENT` key the DataFrame leaves out it raises `BackendCapabilityError` (`preallocated_keys`), as `allocate_primary_keys` does. `resync_sequences` has nothing to repair: an explicit id moves `AUTO_INCREMENT` past it.
- **Bulk updates**: `bulk_update` is a multi-table `UPDATE t AS Tb, (VALUES ROW(?, …), …) AS source (…) SET Tb.col = source.col WHERE …`, each `SET` target qualified (a bare one is ambiguous there). It counts matched rows, a row whose values did not change included, as `update()` does. A text match key compares by the column's collation, as a filter does: on a case- and accent-insensitive one (`utf8mb4_0900_ai_ci`, MySQL 8's default) `"LOTUS"` matches `lotus`, and two keys of the frame that the collation equates both match that row, which ends with one of their values. A `filters=` subquery over the table being written is read through a derived table (error 1093 otherwise), as in `update()`.
- **The many-to-many manager**: `add` is PostgreSQL's idempotent `INSERT … SELECT … WHERE NOT EXISTS (…)`, one statement per target, so it needs no unique key on an explicit through table; `remove`, `clear` and `set` are the same statements on every engine.
- **Plain-column reads** through `M.Model.objects`: `filter` (comparisons, `__@in` lists and subqueries, `Q`/`Qor`, the pattern lookups), joins along relation paths, `on()` and `cjoin_on`, `values`, `order_by`, `limit`/`offset`, `distinct`, `count` (plain, distinct, sliced), `exists`, `first`, `list`, `Exists`/`Subquery`/CTEs over the same, `Sum`/`Avg`/`Count`/`Max`/`Min` with `HAVING`, and `select_for_update` inside a transaction.

What a read means on MySQL:

- **Text compares code points.** A table PormG creates declares its text columns `utf8mb4_0900_bin`, and each connection's collation is the same, so `filter("surname" => "senna")` does not match `Senna`, `"Senna "` (a trailing space) is not `"Senna"`, and `@contains`, `@startswith` and `@endswith` respect case and accents, as on PostgreSQL ([#1265](https://github.com/PingoLee/PormG.jl/issues/1265)). The case-insensitive lookups (`@icontains`, `@iexact`, …) fold case with `LOWER` and stay accent-sensitive. A table PormG did not create keeps its own collation, and MySQL compares by it: under the server default `utf8mb4_0900_ai_ci`, `=` ignores case and accents there.
- **`order_by` on text sorts by code point**, not by a locale (a representation difference: PostgreSQL sorts by its collation's locale).
- **NULL placement** is PormG's default on every engine (last ascending, first descending). MySQL has no `NULLS FIRST`/`NULLS LAST`, so PormG sorts on an `(expr IS NULL)` key first. An ordering expression that binds a value is refused with `BackendCapabilityError`; project it and order by the name. An ordering on a projection named after a column of a table the query reads, such as `values("laps" => "position").order_by("laps")`, puts the projection's own SQL in the key, because MySQL would read `laps` there as the column. Under `distinct()` or a grouping, MySQL can refuse such a key over a projection computed from a column it does not project or group (`position + 1`, a `Case`, `Lag("position")`) with its own error 3065 or 1055; name the projection after no column to order it. When that column's table is joined only by a later term through a nested query's `OuterRef`, PormG cannot tell in time and refuses the ordering with `QueryBuildError`; rename the projection or order by that term first.
- **A boolean** is a `TINYINT(1)` and reads as a `Bool`, from its declared field type, since MySQL has none on the wire.
- **A `DateTimeField`** is a `DATETIME(3)` ([#1270](https://github.com/PingoLee/PormG.jl/issues/1270)), the precision a Julia `DateTime` holds, read in the connection's UTC as a `ZonedDateTime`. A value with digits below the millisecond (a `DATETIME(6)` column PormG did not create, `NOW(6)`) raises `InvalidValueError` instead of losing them.
- **`Sum` over integers** reads as an integer, and a sum past the 64-bit range raises, as on PostgreSQL; MySQL itself computes a `DECIMAL`, which PormG turns back with `DIV 1`. `Avg` over integers reads as a `Float64` (each connection sets `div_precision_increment = 30`, so the mean is not cut to 4 decimals).
- **`select_for_update(no_key = true)`** is refused with `BackendCapabilityError`: MySQL has no lock weaker than `FOR UPDATE` that leaves foreign-key checks free.
- **Division** means what it means on every engine: `F("grid") / 2` divides integers as integers (truncating toward zero, `-9 / 4` is `-2`). MySQL's own `/` keeps the fraction (`7 / 2` is `3.5`), so PormG writes `DIV` between two sides it types as integers and `/` beside a float or a decimal side. A side whose type PormG cannot name (a text column) is refused with `QueryBuildError`, naming the casts that say which division you mean. A quotient over a `Sum` PormG cannot type is refused too, since MySQL's `SUM` of integers is a `DECIMAL`. Division by zero reads `NULL` (the server records a warning), as on SQLite; PostgreSQL raises.
- **`Cast`** maps each type name to the MySQL `CAST` target that holds its meaning: text and the character types to `CHAR` (a size kept), every integer to `SIGNED`, a sized `numeric` to `DECIMAL(p, s)`, a bare `numeric` to `DECIMAL(65, 30)` (MySQL's own bare `DECIMAL` has no fraction), `real` to `FLOAT` (a `Float32`), the doubles to `DOUBLE`, `date` to `DATE`, a timestamp to `DATETIME(3)`, `time` to `TIME(6)`, `json` to `JSON` and `uuid` to `CHAR(36)`. A type with no such target (`boolean`, `interval`, `bytea`, a type of your own) raises `UnsupportedConnectionError` before any SQL; an array or a network type raises `BackendCapabilityError`. Where MySQL computes another value than the cast means, the cast is refused with `QueryBuildError`: a boolean's text (`'1'`, not `'true'`), a date, a timestamp, a time or an interval cast to a number (MySQL reads the digits, `2009-03-29` → `20090329`), and a literal a `numeric(p, s)` cannot hold (MySQL clamps it to the largest value the type holds). A column value too large for its cast is clamped the same way, with only a server warning, where PostgreSQL raises "numeric field overflow": that depends on the row, so PormG cannot refuse it before the query runs. A bare `numeric` (`DECIMAL(65, 30)`) holds 35 digits before the point. An unsized `char` keeps one character, as on PostgreSQL (`CHAR(1)`).
- **`Concat`** skips a NULL operand, as on every engine, and renders `CONCAT_WS('', …)`. PormG never writes `||` for MySQL, where it is a logical OR (`'a' || 'b'` is `0`).
- **Date arithmetic** renders MySQL's date functions, since MySQL's own `+` reads a date as the number its digits spell (`DATE '2009-03-29' + 1` is `20090330`). `F("date") + Day(3)` and every other duration is `± INTERVAL ? <unit>` per component, with years and months as one month count, as PostgreSQL adds them (`2008-02-29` plus one year and one month is `2009-03-29`); a whole number of days, a literal or an integer column, is `± INTERVAL (n) DAY`; `F("date") - F("date")` is the whole days between them (`DATEDIFF`). A DATE shifted by whole days stays a `Date`, and by hours becomes a timestamp. A value PormG cannot type beside a date (`F("date") + Sum("year")`) is refused with `QueryBuildError`. A shift past MySQL's last date, 9999-12-31, reads `NULL` (MySQL records a warning).
- **A `DurationField`** is a `BIGINT` of microseconds, Django's choice for MySQL: MySQL has no interval type, and its `TIME` stops at 838:59:59. It reads back as the `Dates.CompoundPeriod` it reads as on every engine. A filter binds the duration as its microseconds, an equality and `@in` included; ordering, `Sum`/`Avg`/`Max`/`Min`, arithmetic (`F("time") * 2`, `F("time") + F("time")`) and a timestamp difference (`F("start_at") - F("other")`, `TIMESTAMPDIFF(MICROSECOND, …)`) compute in microseconds, exactly; a date shifted by one is `± INTERVAL (d) MICROSECOND`. A product, a quotient and a mean are rounded to the microsecond, half away from zero (beside a `FloatField`, a tie of half a microsecond rounds as MySQL's `DOUBLE` does). `Cast(d, "text")` reads the `HH:MM:SS` text PormG writes (`00:01:20.5`), as on SQLite, where MySQL's own cast would print the count; `Cast(d, "date")`, `"time"` or `"timestamp"` is refused with `QueryBuildError`, since the cast would read the count's digits. What has no meaning is refused with `QueryBuildError` before any SQL, as on SQLite: a duration plus a number, times another duration, or a number compared with one, through any spelling (an expression, a filter either way round, a `Subquery`, a queryset for `@in`, an alias).

- **Conditionals** (`Case`/`When`, `Coalesce`, `Greatest`/`Least`, `NullIf`) render MySQL's own functions. `Greatest` and `Least` skip a NULL argument through the same `COALESCE` rotations as on SQLite, since MySQL's `GREATEST` is NULL when any argument is. A `Decimal` literal inside an expression (a `Case` branch, a `Coalesce` or `Value` operand) binds as `CAST(? AS DECIMAL(p,s))` at its own precision, so it reads back, and orders, as a number rather than text; one past MySQL's DECIMAL (65 digits, 30 after the point) is refused with `QueryBuildError`. A duration beside a value of another type (`Coalesce("fastestlaptime", 0)`) is refused with `QueryBuildError`, declared or not, since one value cannot be both a count and a duration there. A declared `output_field` is `CAST(… AS T)`, except that a boolean declaration over booleans or integers reads `((x) <> 0)` (MySQL casts to no boolean type; over any other value it is refused), and over durations a text declaration reads the `HH:MM:SS` text and a date, time, timestamp or boolean declaration is refused.

- **Math functions** (`Abs`, `Round`, `Floor`, `Ceil`, `Sqrt`, `Power`, `Ln`, `Exp`, `Mod`) render MySQL's own functions, and over an integer `Abs`, `Floor`, `Ceil` and `Round` keep it. MySQL rounds a double half to even (`ROUND(2.5E0)` is `2`), so `Round` over a float rounds it as `DECIMAL(65, 30)`: half away from zero, as on every engine, from the double's shortest digits; a float of `1e35` or more is clamped by that cast. A negative precision rounds to tens, hundreds, … (`Round(125, -1)` is `130`). Over a decimal MySQL computes `Sqrt`, `Exp`, `Ln` and `Power` as a double and `Floor`/`Ceil` as a `BIGINT`; each reads back as the `Decimal` it means, as on SQLite. `Sqrt` of a negative number, `Ln` of 0 and `Mod(x, 0)` read `NULL` (the server records a warning), as on SQLite; PostgreSQL raises. An `Exp` or `Power` past the double range raises, as on PostgreSQL.

- **Date parts** (`Extract`, `ToChar` and the `@year`, `@month`, `@week`, `@week_day`, `@quarter`, `@date`, … transforms) render MySQL's own date functions, numbered as PostgreSQL numbers them: the ISO week is `WEEK(x, 3)` (MySQL's default `WEEK` mode is not the ISO week) and `@week_day` is `DAYOFWEEK`, 1 = Sunday. `Extract` takes SQLite's eleven parts plus `QUARTER`, `EPOCH`, `MILLISECONDS` and `MICROSECONDS`. `EPOCH` is computed from 1970 with `TIMESTAMPDIFF`, exact before 1970 too, where MySQL's `UNIX_TIMESTAMP` answers 0; `EPOCH` of a time raises `BackendCapabilityError`, and so do `CENTURY`, `DECADE`, `MILLENNIUM`, `JULIAN` and the `TIMEZONE` fields. `ToChar` takes the formats of the shared table through `DATE_FORMAT`; any other format raises `BackendCapabilityError`, and a `DurationField` raises `QueryBuildError` (use `Cast(x, "text")`). A date part of a time (`Extract(Cast("start_at", "time"), "year")`, `ToChar` of a time with a year, month or day in its format) raises `QueryBuildError`, since MySQL reads a time's date as today's. The `Extract` parts and the `@` transforms over a `TimeField` column are refused on every engine. A quotient over an `EPOCH` (`Extract(d, "epoch") / 2`, or a sum that holds one) is refused with `QueryBuildError`, as any division over a value PormG cannot type is: `Cast(Extract(d, "epoch"), "numeric") / 2` builds.

- **Text functions** render MySQL's own, with `Length` as `CHAR_LENGTH` (MySQL's `LENGTH` counts bytes). `LPad`/`RPad` with an empty literal fill render the cut alone, as PostgreSQL answers it; a fill column that is empty on a row gives `""` on MySQL.
- **Text and binary values** read back by their column's character set: text as a `String`, a binary type as a `Vector{UInt8}`. MySQL marks every column of a binary collation (PormG's `utf8mb4_0900_bin`) with its binary flag, and MySQL.jl 2.0 decides by that flag, so PormG prepares every statement that returns rows, even one without parameters, to read the character set from its column definitions. A read with no parameters costs one more round trip for it.
- **Window functions** render MySQL's own (`Rank`, `DenseRank` and `RowNumber` cast to a signed integer, so they read back as an `Int64`). `ROWS` and `RANGE` frames render, a `RANGE` interval in MySQL's `INTERVAL 7 DAY` spelling; a `GROUPS` frame or an `EXCLUDE` clause raises `BackendCapabilityError`. A window's `ORDER BY` without `nulls` sorts NULLs first ascending, as SQLite does.

- **Migrations** ([#1268](https://github.com/PingoLee/PormG.jl/issues/1268)): `makemigrations`, `migrate`, `status`, `dry_run`, `check`, `run_once` and `ensure_table!`. A model's tables are created with backtick-quoted names, `ENGINE=InnoDB`, `utf8mb4` and the `utf8mb4_0900_bin` collation. The column types are `BIGINT AUTO_INCREMENT` for an `IDField`, `BIGINT` for a foreign key, a `BigIntegerField` and a `DurationField` (its microseconds), `INT` and `SMALLINT` (the positive fields with a `>= 0` CHECK, not `UNSIGNED`, which turns a subtraction below zero into an error), `TINYINT(1)` for a boolean, `DOUBLE`, `DECIMAL(p,s)`, `VARCHAR(n)` for the fields with a length, `LONGTEXT` for the text fields without one (`TEXT` holds 64 KB), `DATE`, `DATETIME(3)`, `TIME(6)`, `CHAR(36)` for a `UUIDField`, `JSON` and `LONGBLOB`. A literal default on a `LONGTEXT`, `LONGBLOB` or `JSON` column is written as an expression (`DEFAULT ('…')`), the only default MySQL takes there. A `db_default` is one of the portable `CURRENT_TIMESTAMP` and `CURRENT_DATE`. A foreign key is checked at each statement (`deferred_foreign_keys`). MySQL accepts `ON DELETE SET DEFAULT` but enforces it as `RESTRICT`, so a `SET_DEFAULT` key is applied by PormG's `delete` and refused by MySQL on a delete PormG does not make. An index has no partial form (`partial_indexes`), and `method`, `opclasses` and `include` are refused (`index_methods`). A key or index over a field written as `LONGTEXT`, `LONGBLOB` or `JSON` (such as a `TextField`, `EmailField`, `ImageField`, `FileField`, `PasswordField`, `BinaryField` or `JSONField`) is refused by `makemigrations` (`unbounded_text_indexes`): MySQL indexes those columns only by a prefix; declare a `CharField`. A key over `CharField`s longer than InnoDB's 3072 bytes (4 bytes a character in `utf8mb4`: one `max_length` above 768, or a composite whose lengths add up past it) is refused by MySQL at `migrate` (error 1071), after the statements before it committed. A name a model writes longer than 64 characters is refused by MySQL (error 1059); an index name PormG derives (`<table>_<cols>_uniq`, a many-to-many join table's) is cut to 55 characters and 8 hex digits of its hash there. PormG keeps index names unique across a database's tables on every backend, though MySQL scopes them per table.
- **Changes to a table that exists.** A column change is one `ALTER TABLE` statement whose clauses carry it whole (so it applies or does not): `MODIFY COLUMN` restating the column's type, nullability, default and `AUTO_INCREMENT`, which MySQL replaces together, PormG's CHECKs dropped and added by name, the column's own unique index, the primary key. A renamed column drops and re-adds the CHECKs MySQL will not let it take along (error 3959), and renames its unique index; the drop makes such a plan destructive (`destructive = true`), as any constraint drop is. A dropped foreign key takes the index InnoDB made for it. A dropped table is dropped with the session's foreign-key checks off, as PostgreSQL's `CASCADE` would remove the keys of the children the same plan alters. A `db_index` turned off on a column that keeps its foreign key is refused by MySQL (error 1553: InnoDB keeps every foreign key indexed), and retyping a column a foreign key joins is too (error 3780).
- **The row pre-checks** count, before any statement runs, the rows a change would fail: MySQL's strict `sql_mode` fails the `ALTER` on a value that does not convert or fit, part-way through a plan. A shorter `VARCHAR` counts trailing spaces too (MySQL refuses them, where PostgreSQL trims them); a narrower integer or decimal, a NULL under `NOT NULL`, a duplicate under a new key, a key's orphans, and text into a number, a date, a time, JSON or a UUID are each counted, and `migrate` refuses the plan with `MigrationPrecheckError` naming the counts. Text MySQL would convert by rounding (`'12.5'` into an integer) is counted as failing, as PostgreSQL refuses it. A `NOT NULL` column added without a default is refused over existing rows: MySQL would fill them with `0` or `''`. What MySQL applies and changes — a lower decimal scale, a timestamp's time of day dropped — takes `destructive = true`, as on PostgreSQL.
- **`migrate`** runs a plan's statements on one connection, renewed afterwards. `lock_timeout` sets that connection's `lock_wait_timeout` (whole seconds); `statement_timeout` is refused (`statement_timeouts`), since MySQL bounds no DDL statement's run time. A second instance waits on the `GET_LOCK`, and its schema check runs inside the lock (before it, a half-applied plan reads as changed).
- **`run_once`** takes the migration lock and commits the step and its record together, as on PostgreSQL. A DDL statement inside a MySQL step commits the transaction implicitly, so keep a step to writes. **`ensure_table!`** drops the table again when a statement after its `CREATE TABLE` fails.

Not yet, phase 4c's: a `db_default` pinned per engine (MySQL takes the portable `CURRENT_TIMESTAMP` and `CURRENT_DATE`), a functional index and a declared `CheckConstraint`, each refused with `UnsupportedConnectionError` naming the phase before any SQL is sent; and `inspectdb` for MySQL (`import_models_from_mysql`).

Each connection runs in UTC (`time_zone = '+00:00'`), with `utf8mb4`, the `utf8mb4_0900_bin` connection collation, and MySQL 8.4's default `sql_mode`, so neither the server's global settings nor a DBA's change to them alters what a statement means. A statement whose connection is lost is never retried: MySQL reports the same error whether or not the statement ran ([MySQL.jl#248](https://github.com/JuliaDatabases/MySQL.jl/issues/248)). That includes a connection the server closed while it sat idle in the pool past the server's `wait_timeout` (8 hours by default, often less on a hosted server): its next statement raises `OperationalError`, and the pool renews the connection after it. `idle_timeout:` does not prevent this: it closes only the overflow connections above `pool_size` ([Advanced Configuration](configuration/advanced.md)), and the base connections stay open however long they sit idle. Keep the server's `wait_timeout` above the application's longest idle period, or expect the first statement after such a gap to fail once with `OperationalError` while the pool renews the connection.

## What the capability table leaves out

- **A version PormG does not check.** `ON CONFLICT` (`bulk_insert(on_conflict = …)`, `update_or_create`, `get_or_create`) needs SQLite 3.24, and an older library raises SQLite's own error. A query feature newer than your PostgreSQL server fails with PostgreSQL's own error ([PostgreSQL Guide](postgres.md#Server-versions)).
- **A number that depends on a version.** SQLite accepts 999 bind parameters per statement before 3.32 and 32766 from it. PormG sizes `bulk_insert` and `bulk_update` batches to the library it loads, so this is a limit, not a feature.
- **A feature one backend supports only in part.** For example, `ToChar` formats or `Extract` parts that SQLite cannot spell, or a cast to a time type. Each raises `BackendCapabilityError` where it is used, and its page says which forms work.
- **A gap in PormG, not in an engine.** SQLite has explicit window frames, but PormG does not render `WindowOver(frame = …)` there yet, and raises `BackendCapabilityError` saying so ([Window Functions](read/window_functions.md)).
- **A difference in what a query returns.** When two backends would compute different values or rows for the same query, PormG refuses it on the backend that departs, or documents the difference. That is not a missing feature ([Functions and Dates](read/functions_and_dates.md); for a declared scale or a cast to an integer, [Rounding](read/rounding.md)).
