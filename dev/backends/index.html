Backend Capabilities

PormG runs on PostgreSQL and SQLite; MySQL is planned for the first registered release (#1130). Most of what it does means the same on both. Some features exist on one backend only, and PormG does not emulate a feature a backend lacks. It raises BackendCapabilityError instead, and the message names the feature, the backend you are on, and the backends that support it:

The @jcontains lookup (JSONB @>) needs JSONB containment and key operators (`@>`, `?`, `?|`, `?&`),
which SQLite does not support (supported on PostgreSQL).

The table below is the list PormG checks. A unit test fails when this page and the code disagree.

Some features exist from a server version on. Their cell says which, as from 13 (PostgreSQL's server_version_num major version) or from 3.25.0 (the SQLite library PormG loads). PormG asks the server its version where it needs the answer. Where a feature is refused, an older server gets BackendCapabilityError naming both versions:

A window function needs SQLite 3.25.0 or newer, for window functions (`OVER (…)`); the SQLite
library PormG loads is 3.24.0.

Where PormG reads the schema, an older server is not refused: the feature reads as absent, which is exact there, because a server without the feature has none of it.

Guarantees that rest on an engine feature

Some promises PormG makes hold because the engine underneath provides something, not because PormG computes them. They hold on PostgreSQL and SQLite, each in its own way. A backend added later states its own column here: where it cannot keep a promise, PormG refuses or documents the difference rather than emulating it.

PromisePostgreSQLSQLite

Two promises are PormG's own meaning rather than an engine's, and hold on every backend by construction: F("grid") / 2 divides integers as integers, and a NULL Concat operand is skipped. A backend whose operator computes something else gets a different rendering, not a different answer (Functions and Dates).

What the capability table leaves out

  • A version PormG does not check. ON CONFLICT (bulk_insert(on_conflict = …), update_or_create, get_or_create) needs SQLite 3.24, and an older library raises SQLite's own error. A query feature newer than your PostgreSQL server fails with PostgreSQL's own error (PostgreSQL Guide).
  • A number that depends on a version. SQLite accepts 999 bind parameters per statement before 3.32 and 32766 from it. PormG sizes bulk_insert and bulk_update batches to the library it loads, so this is a limit, not a feature.
  • A feature one backend supports only in part. For example, ToChar formats or Extract parts that SQLite cannot spell, or a cast to a time type. Each raises BackendCapabilityError where it is used, and its page says which forms work.
  • A gap in PormG, not in an engine. SQLite has explicit window frames, but PormG does not render WindowOver(frame = …) there yet, and raises BackendCapabilityError saying so (Window Functions).
  • A difference in what a query returns. When two backends would compute different values or rows for the same query, PormG refuses it on the backend that departs, or documents the difference. That is not a missing feature (Functions and Dates).
